# Metadata and additions recipes

Read after identifying the failing native and generated declarations. The
`com.example` examples below are illustrative shapes, not existing APIs to paste
into an unrelated binding. Put `attr` elements inside `<metadata>` in
`Transforms\Metadata.xml`; put partial C# types in `Additions`.

## Select the exact API

Copy the XPath from the generated member's comment, then verify it against the
input `api.xml`. Keep Java names and generic type strings in the selector even
when C# uses different names. Escape `<`, `>`, and `&` in XML attribute values.

For example, distinguish two `get` methods by their generic Java parameter:

```xml
<metadata>
  <attr path="/api/package[@name='com.example']/class[@name='ValueStore']/method[@name='get' and count(parameter)=1 and parameter[1][@type='com.example.Key&lt;java.lang.Boolean&gt;']]" name="managedName">GetBoolean</attr>
  <attr path="/api/package[@name='com.example']/class[@name='ValueStore']/method[@name='get' and count(parameter)=1 and parameter[1][@type='com.example.Key&lt;java.lang.Integer&gt;']]" name="managedName">GetInteger</attr>
</metadata>
```

Use actual parameter/return attributes from the artifact if generic metadata is
unavailable. Check expected match counts and regenerated declarations.

Java **source** cannot overload solely by return type. JVM descriptors include
return types, however, and Kotlin-generated bytecode, bridges, or erased generic
bindings can expose signatures that collide in C#. Diagnose the actual class
file; do not repeat the claim that Java source permits return-only overloads.

Use `managedName` to change a managed namespace/type/method, not `name`, which can
alter the Java identity. Leave generated `[Register]` attributes and JNI method
IDs alone. A method rename should retain the original Java target.

## CS0535: generic interface parameter mismatch

A Java specialization can generate a typed `Accept` while the bound interface
requires `Accept(Java.Lang.Object?)`. This is not arbitrary parameter covariance:
inspect generic specialization, erasure, and bridge methods.

When the generated class already has `Accept(Java.Util.Functions.IBiConsumer?)`
and implements `Java.Util.Functions.IConsumer`, an addition can forward:

```csharp
using Android.Runtime;

namespace Example.Binding;

public partial class ConsumerConfig
{
    public virtual void Accept(Java.Lang.Object? value)
    {
        Accept(value?.JavaCast<Java.Util.Functions.IBiConsumer>());
    }
}
```

Match the real class, parameter, nullability, and virtual/sealed contract. Verify
that the native generic contract actually requires this type before casting.
`JavaCast<T>()` is useful when a JNI peer needs a managed interface wrapper; a
normal C# cast is appropriate only when the managed object implements that type.
Test null, correct-type, and invalid-type behavior; don't catch a failed cast and
silently drop the callback. Ensure forwarding resolves to the typed overload, not
itself. A `managedType` transform on the parameter is another option, but compare
the generated marshalling and public API before choosing it.

## CS0738: interface return types and properties

C# interface implementation still requires a matching contract; a more-specific
return type alone does not implement an ordinary non-variant interface member.
Keep the useful typed public API with a forwarding explicit implementation when
the conversion is valid. For example, assume a vendor's generated binding contains
this interface (context only; do not redeclare it in `Additions`):

```csharp
namespace Example.Binding;

public partial interface IWidgetCloner
{
    Java.Lang.Object Clone();
}
```

The generated `Widget` derives from `Java.Lang.Object`, implements
`IWidgetCloner`, and already exposes `public Widget Clone()`. Add only the
forwarding partial class to `Additions`:

```csharp
namespace Example.Binding;

public partial class Widget
{
    Java.Lang.Object IWidgetCloner.Clone() => Clone();
}
```

Use the actual vendor interface that declares the method. `Java.Lang.ICloneable`
is a marker interface with no `Clone()` member, so it cannot be used for this
explicit implementation.

For collections, inspect both managed types. Do not assume a nongeneric `IList`
also implements `IList<string>`. Use an established Java collection projection or
a deliberate conversion only after deciding whether identity, mutability, and
live-view semantics must be preserved. An explicit interface property must return
the actual data, not an empty list or a default just to compile.

`managedReturn` is an alternative for changing the managed method return:

```xml
<attr path="/api/package[@name='com.example']/class[@name='Widget']/method[@name='clone' and count(parameter)=0]" name="managedReturn">Java.Lang.Object</attr>
```

This changes the managed API contract. Inspect regeneration and consumer impact;
do not edit the Java `return` attribute or JNI signature to force compatibility.

### Do not infer unsupported generics from a malformed transform

The android-libraries example tried
`System.Collections.IList&gt;System.String&lt;`. Its brackets are reversed and its
namespace is not the generic collection namespace. The corresponding C# type
spelling is `System.Collections.Generic.IList<System.String>` (XML text uses
`&lt;` and `&gt;` in that order).

That failing example does **not** establish that every generic `managedReturn`
is unsupported. Check syntax, then test the actual generator version and its
marshalling. If it still fails, use a correct forwarding addition where feasible
and capture a minimal generator repro. Do not promise a spelling correction alone
will make a generic transform work.

## CS0534 and CS0115: class overrides

Modern C# supports covariant returns in supported class-override scenarios. Older
guides saying "C# cannot do covariance" are too broad. Check the generated base
method, return type, accessibility, and whether the generator emitted an override.

Use `managedReturn` to match a base contract when necessary. After confirming a
real base method exists, a targeted modifier repair can be:

```xml
<attr path="/api/package[@name='com.example']/class[@name='Widget']/method[@name='copy' and count(parameter)=0]" name="managedOverride">override</attr>
```

For an interface-only implementation incorrectly emitted as `override`, use
`virtual`. `managedOverride` also accepts `none` in supporting SDKs (introduced
in .NET 7) when neither modifier is appropriate. Do not force `override` over an
unresolved/missing base API; repair that dependency first.

## Three different event collisions

### Duplicate EventArgs classes

Use `argsType` on the listener **method**, choosing unique descriptive names:

```xml
<attr path="/api/package[@name='com.example']/interface[@name='DownloadListener']/method[@name='onError' and count(parameter)=1 and parameter[1][@type='int']]" name="argsType">DownloadErrorEventArgs</attr>
<attr path="/api/package[@name='com.example']/interface[@name='UploadListener']/method[@name='onError' and count(parameter)=1 and parameter[1][@type='int']]" name="argsType">UploadErrorEventArgs</attr>
```

### Duplicate events from add/set listener registration

Give the projected events distinct `eventName` values, or disable just the
redundant projection:

```xml
<attr path="/api/package[@name='com.example']/class[@name='Client']/method[@name='setChangeListener' and count(parameter)=1 and parameter[1][@type='com.example.ChangeListener']]" name="eventName"></attr>
```

The listener registration method remains callable; this is not `remove-node`.
Keep the intended event projection from the other registration method.

### Duplicate Handler fields in a listener implementor

For overloaded callbacks, distinguish the managed method name, since internal
handler field names are derived from it:

```xml
<attr path="/api/package[@name='com.example']/interface[@name='ChangeListener']/method[@name='onChange' and count(parameter)=2 and parameter[1][@type='java.lang.String'] and parameter[2][@type='java.lang.Object']]" name="managedName">OnChangeWithValue</attr>
```

Renaming both overloads to the same new name recreates the collision. Changing
only `argsType` does not necessarily repair a duplicate handler field.
